# YAML Frontmatter Doctrine

## 0. Why this document exists

Two recent notes broke in two different ways, and the two ways matter differently:

1. **`janitor-builder-deadlock-...`** — hard parse failure. Obsidian / any YAML parser
   throws `mapping values are not allowed in this context` and the file may fail to
   index at all.
2. **`forecast-...smoke-test...`** — silent truncation. The file *parses fine* and
   *looks fine*, but everything after a stray `#` was silently discarded as a YAML
   comment. Nobody sees an error. The data is just gone.

Case 2 is the one to actually be afraid of. A crash gets noticed and fixed. A silent
truncation sits in the vault for months, quietly lying to every agent that reads it.

The root cause in both cases was identical: **narrative sentences were written
directly into YAML scalar values without quoting.** This is not a one-off typo, it's
a systemic pattern — every skill that generates frontmatter (`frontmatter-gen`,
Janitor, Curator, Oracle write-backs) needs to internalize the same handful of rules,
or this keeps happening at the current rate indefinitely.

---

## 1. The exact bugs, annotated

```yaml
status: raw — Curator: link from [[janitor-builder-deadlock-3bug-verify-2026-07-27]]; INDEX entry optional
```

| Fragment | Why it breaks |
|---|---|
| `Curator: ` | Second unescaped `": "` in an unquoted scalar → parser thinks a new mapping key just started. **Hard error.** |
| `[[janitor-builder...]]` | `[` is a YAML flow-sequence indicator. Safe *mid-string* here only because it isn't the first character of the scalar — but it's one refactor away from being unsafe. |
| `—` (em dash) | Not a YAML indicator character, harmless on its own, but a signal that "prose" is being written where a scalar is expected — the real smell to catch. |

```yaml
status: raw — Curator: triage (link from [[forecast-pilot-01]] Deviations; supersedes the #19 "pulled" diagnosis there)
```

| Fragment | Why it breaks |
|---|---|
| `Curator: ` | Same hard-error pattern as above. |
| ` #19` | Space + `#` = **start of a YAML comment**. Everything after this point in the line — the actual diagnosis — is silently deleted on parse. This is the dangerous one. |
| `"pulled"` | Unescaped double quotes inside an unquoted scalar. Depending on the parser this either errors or produces garbage. |

## 2. The single rule underneath all of it

> **If a YAML scalar value contains anything other than a short, single-purpose
> token (a tag, a date, a single wikilink, a status word), it must be wrapped in
> double quotes — and even then, some content still doesn't belong in frontmatter
> at all.**

Frontmatter is a metadata index, not a changelog. The moment a value becomes a
sentence with reasoning, justification, or a narrative trail ("Curator: link from
X; INDEX entry optional"), it has stopped being metadata and started being content
— and content belongs in the note body, not the YAML block.

---

## 3. Hard rules for every skill that emits frontmatter

These are not style preferences. They are parser-safety requirements. Any skill
(`frontmatter-gen`, Janitor writers, Curator writers, Oracle writers) must enforce
all of them before writing a YAML block:

### Rule 1 — Quote any scalar containing a colon-space
If a value contains `": "` anywhere after its first character, wrap the whole
value in double quotes. YAML permits exactly one unquoted `key: value` split per
line; a second one is always a bug.

### Rule 2 — Quote any scalar containing a space followed by `#`
`" #"` (space-hash) starts a comment in unquoted context and silently truncates
everything after it. This is the single most dangerous pattern because it fails
silently. Any generated string containing a literal `#` preceded by whitespace
**must** be quoted, with no exceptions — this includes references like `#19`,
`#issue-42`, hashtag-shaped IDs, etc.

### Rule 3 — Never lead a plain scalar with an indicator character
`[`, `{`, `*`, `&`, `!`, `|`, `>`, `'`, `"`, `%`, `@`, `` ` ``, `-` (with trailing
space), `?` (with trailing space), and `#` (at line start) are all YAML indicators.
If a value would start with one of these, quote it. A leading `[[wikilink]]` as
the *entire* value must be quoted (`"[[note-name]]"`), even though a wikilink
buried mid-sentence in an already-quoted string is fine.

### Rule 4 — Escape internal double quotes, or use single quotes as the outer wrapper
If the value itself needs to contain `"pulled"`-style internal quoting, either:
- escape it: `"...the #19 \"pulled\" diagnosis there"`, or
- switch the outer quote style: `'...the #19 "pulled" diagnosis there'`

Never leave internal double quotes unescaped inside a double-quoted scalar.

### Rule 5 — Narrative content does not belong in frontmatter values at all
This is the structural fix, not just the syntactic one. `status`, `verdict`, and
similar fields should hold a **short controlled-vocabulary token**
(`raw`, `triage`, `ok`, `needs-review`, `superseded`), never a sentence with
reasoning attached. Any explanatory trail — "Curator: link from X; INDEX entry
optional," "supersedes the #19 diagnosis" — belongs in one of:
- a `## Curator notes` section in the note body, or
- a dedicated `notes:` field holding a short quoted string, separate from `status`.

If a skill is tempted to write a sentence into a frontmatter value, that is the
signal to instead write a body section. This eliminates the whole bug class at
the source rather than just quoting around it.

### Rule 6 — Wikilinks as list items are the correct pattern — keep using it
The `related:` block in both files is written correctly:
```yaml
related:
  - "[[forecast-pilot-01]]"
  - "[[ledger]]"
```
Quoted, one link per list item, no embedded prose. This is the model to generalize
outward to every other field that references other notes — never inline multiple
wikilinks into a single prose `status` string the way both broken files did.

### Rule 7 — When in doubt, quote everything
The cost of quoting a value that didn't strictly need it is zero. The cost of not
quoting one that did is a silent data loss bug that survives in the vault for
months. Default posture for any generated scalar longer than a single word: quote
it.

## 4. Corrected versions of both files

```yaml
---
tags: [inbox, janitor, oracle, harness, deadlock]
date: 2026-07-27
status: raw
verdict: "ok — Oracle refreshed (both files), two spec deviations, both evidence-backed"
job: "queue.md l.66 — ORACLE REFRESH — ENGINE DEADLOCK ALERT"
curator_note: "Link from [[janitor-builder-deadlock-3bug-verify-2026-07-27]]; INDEX entry optional"
related:
  - "[[janitor-builder-deadlock-3bug-verify-2026-07-27]]"
  - "[[janitor-builder-deadlock-emptyqueue-2026-07-27]]"
  - "[[quant-pilot-02-execution-2026-07-27]]"
  - "[[quant-row1-date-reconciliation-2026-07-27]]"
  - "[[tool-pilot-01-publish-checklist]]"
---
```

```yaml
---
tags: [inbox, quant, forecasting, smoke-test, decision-prep, ledger-row-1]
date: 2026-08-01
status: raw
curator_note: "Triage (link from [[forecast-pilot-01]] Deviations; supersedes the #19 \"pulled\" diagnosis there)"
related:
  - "[[forecast-pilot-01]]"
  - "[[forecast-scorer-harness-smoke-2026-07-22]]"
  - "[[critic-forecast-pilot-01-2026-07-22]]"
  - "[[ledger]]"
---
```

Note the structural change: `status` is now a clean controlled-vocabulary token
(`raw`), and the narrative trail moved into a separate `curator_note` field that
is fully quoted with the internal `"pulled"` properly escaped. This is more
resilient than just quoting the original single field, because `status` staying
short and enumerable means downstream agents (Janitor, Oracle) can pattern-match
on it reliably instead of regex-scraping a sentence.

## 5. On "kepano" conventions

Steph Ango's (kepano's) frontmatter conventions for Obsidian — the ones most
widely copied into vault templates — follow exactly the discipline above:
short, single-purpose scalar fields (`title`, `date`, `tags`, `status`), lists
for anything multi-valued, and prose kept out of the YAML block entirely. The
pattern of narrative `status`/`verdict` strings in your two broken files is a
drift away from that convention, not a variant of it. Re-aligning
`frontmatter-gen`'s output schema to kepano-style — few fields, all short,
all either enums or quoted strings or lists — is the same fix as Rule 5 above,
just framed as "match the standard" rather than "avoid the bug."

Suggested canonical field set going forward:

```yaml
tags: [ ... ]        # array, unquoted plain words are fine here — no colons/hashes in tags
date: YYYY-MM-DD      # bare date, never quoted, never narrative
status: <enum>        # single controlled-vocabulary word, always unquoted-safe by construction
role: <enum>           # e.g. Janitor, Curator, Oracle — single word
verdict: "<short quoted string>"   # quoted if it has any punctuation at all
job: "<quoted string>"
curator_note: "<quoted string>"    # new: catch-all for narrative trail, always quoted
related:
  - "[[wikilink]]"     # always quoted, one per line
```

## 6. What to change in `frontmatter-gen` (and any sibling skill)

Concrete, actionable changes to push into the skill so this becomes structural
rather than something a human has to keep catching by eye:

1. **Pre-write validation pass.** Before emitting any YAML block, run every
   scalar value through a check for: `": "` anywhere but the key position,
   `" #"` anywhere, unescaped `"`, and leading indicator characters. If any hit,
   auto-quote (and auto-escape internal quotes) before writing.
2. **Schema enforcement.** `status` and `role` fields should be validated against
   a fixed enum list, not accept freeform text. If the content doesn't fit the
   enum, it goes to `curator_note` instead, quoted.
3. **Round-trip self-check.** After generating a frontmatter block, actually
   parse it back (e.g. with a YAML parser call) before returning it to the user.
   If parsing fails, or if the parsed value length is shorter than the intended
   string length (the silent-truncation signature), regenerate with full quoting.
   This single check would have caught both bugs in this document automatically.
4. **Never inline multiple `[[wikilinks]]` into a prose field.** If a generated
   value would contain more than one wikilink, that's a signal it should be a
   `related:` list item (or split across list items) instead of a single string.
5. **Update `skill-judge`'s audit checklist** to flag any skill whose generated
   frontmatter contains unquoted scalars with embedded colons, hashes, or quotes
   — this turns the fix in this document into an automatically enforced standard
   across the whole skill ecosystem, not just `frontmatter-gen`.

Once points 1–3 are implemented as an actual pre-write validation step (not just
a documented convention), this entire bug class becomes structurally impossible
for any note the local agents generate — not just less likely.
