## FM-1 · Proxy storm (2026-07-21)

- **Symptom:** 17 consecutive ticks died `exit1 · API Error: Unable to connect to API (ConnectionRefused)`; the same Scout job re-fired and failed every wave for ~4h.
- **LOG evidence:** `2026-07-21T00:11:18Z → 04:02:51Z` (lines 23–39, 17× ConnectionRefused); recovery `04:19:45Z ok` (line 40); fix recorded in the `manual` line at 04:30-ish (line 41).
- **Root cause:** the API router ran as a *child of a session* — it flapped and died, taking every tick with it; the runner had no preflight, so it dispatched straight into a dead endpoint and the poisoned-job retry loop re-fired the same job into the wall.
- **Shipped fix:** (1) router made persistent — `universal-router.service` (systemd --user, `Restart=always`, :8705; ops note `_harness/ROUTER.md`); (2) runner.sh gained the proxy preflight — **Guard 3** (`runner.sh:55-64`): TCP probe of `ANTHROPIC_BASE_URL` once per wave, `SKIP(PROXY_DOWN)` + exit 0, jobs preserved; (3) poisoned-job breaker — `[!]` quarantine after `MAX_JOB_RETRIES=3` consecutive REAL fails (`config.env:25`; infra fails never count).
- **Regression check:** point `ANTHROPIC_BASE_URL` at a dead port → wave logs one `SKIP(PROXY_DOWN)` line and exits 0 in <1s with zero sessions spawned and the queue untouched.

## FM-2 · Trust-bug hang (2026-07-21)

- **Symptom:** sessions hung silently to `TIMEOUT(900s)` with `(no output captured)`; where output survived it showed `Ignoring 25 permissions.allow entries from .claude/settings.local.json: this workspace has not been trusted`.
- **LOG evidence:** `2026-07-21T04:45:01Z` + `06:45:01Z` TIMEOUTs carrying the trust warning (lines 42, 50); `(no output captured)` TIMEOUT cluster `07:33:42Z → 09:15:01Z` (lines 53–54, 57, 59, 62, 64).
- **Root cause:** cron's cwd is `$HOME`, so headless `claude` never saw the vault's `.claude` allowlist + trust → it sat on an interactive permission dialog nobody could click, burning the full 900s per session.
- **Shipped fix:** (1) `cd "$VAULT"` in runner.sh (`runner.sh:22`) + worker.sh (`worker.sh:24`) so sessions run from the vault root and pick up allowlist + trust (wave-engine upgrade, LOG line 51); (2) `projects["/home/fabio"].hasTrustDialogAccepted=true` set in `~/.claude.json` (Janitor TRUST+HEALTH job, LOG lines 54/56, `journal/sessions/janitor-trust-health-2026-07-21.md`). `SESSION_TIMEOUT=900` deliberately kept — it IS the hang guard.
- **Regression check:** launch a worker from a cron-like cwd (`$HOME`) → output contains no "Ignoring … permissions.allow" warning and the session ends on its verdict, not at 900s.

## FM-3 · Quota storm (2026-07-23 → 07-26, ~3 days dark)

- **Symptom:** 12 Steward sessions each burned ~314–334s then died `exit1 · API Error: Request rejected (429) · Your token-plan 1-week quota has been exhausted. The quota will reset at 07-27 04:07:00 UTC.`; the engine produced nothing for ~3 days.
- **LOG evidence:** first 429 `2026-07-23T12:20:34Z` (line 270); repeats at lines 294, 318, 342, 366, 391 (07-23/24), 415, 439, 464, 488 (07-25), 512, 536 (07-26) — 12× total; "engine dark ~3d" noted by Steward #20 (line 560); breaker job bridged line 561, shipped `2026-07-26T13:23:24Z ok` (line 562; digest `journal/sessions/janitor-quota-breaker-2026-07-26.md`).
- **Root cause:** the weekly token-plan quota was exhausted and the reset time was *in the error text itself*, but the runner kept dispatching — each wave re-hit the same 429 wall at ~330s a head. Guard 3 (FM-1) probes a dead router, not quota exhaustion; that was the gap.
- **Shipped fix:** **Guard 4** quota hold (`runner.sh:66-84`) + `quota_detect()` (`runner.sh:87-101`): on a 429 quota error, parse the reset timestamp from the API error text, latch it as epoch seconds in `_harness/.quota_hold`, and every wave exits on a cheap `SKIP(QUOTA)` line until the reset passes → `QUOTA_RESUMED` clears the hold (corrupt hold file self-heals). Builder/council suppressed while held (`runner.sh:340-341`) — they'd die on the same 429.
- **Regression check:** feed a worker output file containing the quota error text to `quota_detect` → `.quota_hold` holds the parsed epoch; a wave before reset logs `SKIP(QUOTA)` and spawns nothing; after the epoch the hold clears and `QUOTA_RESUMED` logs (the shipped done-evidence was exactly this simulated round-trip).

## FM-4 · Builder-lane deadlock ×2 (2026-07-26 + 07-27 — routing patched twice in 24h)

**FM-4a · Structural deadlock — builder-only queue can never dispatch.**
- **Symptom:** after the builder-routing change shipped (2026-07-26 20:26Z), a queue holding ONLY builder-lane jobs sat unchecked ~6h while every wave logged `SKIP(EMPTY_QUEUE)`; the bridge even merged two MORE proposals into the deadlock.
- **LOG evidence:** ROW-4 EXECUTE bridged `2026-07-27T01:00:01Z` (line 609) + INDEX SWEEP `[builder]` bridged `01:45:01Z` (line 612) sat unchecked; `SKIP(EMPTY_QUEUE)` wall `02:00 → 06:30Z` (lines 613–631); bridge merges into the deadlock at lines 634–635; fix shipped `13:38:01Z ok` (line 658; digest `journal/sessions/janitor-builder-deadlock-emptyqueue-2026-07-27.md`, 27/27 sandboxed-wave assertions); first production `SKIP(BUILDER_WAIT)` proves the path live at `14:30:01Z` (line 662).
- **Root cause:** the worker claim loop defers builder-lane jobs (`runner.sh:234-237`) → `J_JOB` empty → the empty-queue branch bridged or throttle-exited (`exit 0`) BEFORE the builder dispatch section was ever reached. The 20:26Z shipping test simulated a tagged job routing, but never the *builder-only queue* that actually triggers.
- **Shipped fix:** empty-queue branch now checks `builder_jobs_pending` (`runner.sh:127-133`) → on a serial-lane wave it falls through to the builder section; otherwise logs `SKIP(BUILDER_WAIT)` and exits — and the bridge never merges while builder jobs are stranded (`runner.sh:250-265`), gated by `serial_lane_this_wave` (`runner.sh:135-141`).

**FM-4b · Mis-routing — `[builder]` tag matched as a substring.**
- **Symptom:** engine dispatched ZERO jobs ~09:00 → 13:38Z; all 4 unchecked queue jobs classified as builder-lane, so the worker lane skipped every one.
- **LOG evidence:** the fix job at queue.md l.61 quoted the `[builder]` tag in its OWN body and was mis-routed (job text preserved at LOG line 656); Oracle deadlock alert confirms "deadlocked 09:00→13:38Z" (line 667); fix verified in-tree `14:05:09Z ok` (line 660; digest `journal/sessions/janitor-builder-deadlock-3bug-verify-2026-07-27.md`, sandbox acceptance tests (i)(ii)(iii)).
- **Root cause:** `job_lane()` used `grep -qiF` on the opt-in tag — a literal substring match anywhere in the job text, so any job *mentioning* `[builder]` routed to the builder lane.
- **Shipped fix:** the tag matches only as a LEADING token — anchored ERE `'^[[:space:]]*(\[[^]]*\][[:space:]]+)?\[builder\]'` (bare, or right after the `[Role]` prefix) at `runner.sh:120`; `BUILDER_ROUTE_PATTERN='^\[Quant\][^:]*EXECUTE'` anchored at `config.env:38` so `'[Critic] … before the EXECUTE job'` stays on the worker lane.
- **Regression check (both):** run `job_lane` over (a) a job merely quoting `[builder]` in its body → `worker`; (b) a real `[Quant] … EXECUTE` job → `builder`; then simulate a builder-ONLY queue → its job dispatches on the next builder-eligible wave (`BUILDER_EVERY=2`) with NO bridge merge.

## FM-5 · Monolithic-job timeout ×4 (2026-07-26/27, ~3600s burned)

- **Symptom:** data-heavy jobs died `TIMEOUT(900s)` with no output — zero artifacts for ~3600s of compute — then the same jobs ran fine once correctly laned.
- **LOG evidence:** ROW-3 EXECUTE timed out TWICE on the worker lane (`2026-07-26T14:30:01Z` + `14:45:01Z`, lines 566–567) then finished in 741s on the builder lane (`14:57:22Z`, line 568); ROW-4 EXECUTE timed out at 900s/901s TWICE *on the builder lane* (`2026-07-27T07:06:20Z` + `08:33:19Z`, lines 633, 638) then ran 1008s ok post-fix (`13:54:49Z`, line 659). 900+900+900+901 = 3601s burned.
- **Root cause:** (a) data-heavy jobs exceed the worker lane's `SESSION_TIMEOUT=900`/`MAX_TURNS=40`; (b) even laned to builder, `worker.sh` capped EVERY model attempt at `SESSION_TIMEOUT=900` regardless of the budget argument (`worker.sh:67`), so `BUILDER_BUDGET=2400` never applied.
- **Shipped fix:** (1) builder-lane routing — `job_lane` + `pick_builder_job` + worker claim-loop skip + `BUILDER_ROUTE_PATTERN` (LOG line 590, `runner.sh:118-169,234-237`; digest `journal/sessions/janitor-builder-lane-routing-2026-07-26.md`); (2) `worker.sh:67` — `[[ "$slot" == "builder" ]] && per=$budget`, so the builder slot's per-attempt cap = its budget; (3) `pick_builder_job` gained the fail-streak breaker (`runner.sh:143-169`) — before it, one perpetually-timing-out builder job would wedge the lane forever; (4) process: monoliths get decomposed into resumable ≤900s cache-backed steps (LOG lines 664–665, [[quant-pilot-02-PLAN]]). Worker `SESSION_TIMEOUT=900` deliberately NOT raised — it guards the FM-2 hang.
- **Regression check:** a builder-tagged job dispatches with per-attempt cap = `BUILDER_BUDGET` (2400s), not 900s; a builder job timing out `MAX_JOB_RETRIES` times is quarantined `[!]` and the lane advances to the next job.

## FM-6 · Duplicate dispatch ×2 (2026-07-27) — timeout-credit breaker SHIPPED 2026-07-31 (bridge-duplicate sub-case still open)

- **Symptom:** the same work ran two–three times: a timed-out session that had ALREADY written its artifact got re-dispatched, and two near-identical fix jobs raced.
- **LOG evidence:** (a) ROW-1 date reconciliation timed out `08:00:01Z` (line 636) but had written `inbox/quant-row1-date-reconciliation-2026-07-27.md`; the re-dispatch at `08:18:18Z` (line 637) reported `VERIFIED-DUPLICATE … already done this morning`. (b) The builder-deadlock FIX job: `TIMEOUT` `13:30:01Z` (line 657) + a parallel near-identical fix job landing the change at `13:38:01Z` (line 658) + the timed-out job re-dispatched and reporting `already in-tree … independently verified` at `14:05:09Z` (line 660) — the fix ran 3×, twice after the change had already landed.
- **Root cause:** the runner marks a job `[x]` ONLY on `verdict == ok` (`runner.sh:333`); a session that does the work but times out (or loses its verdict file) leaves the job unchecked → re-claimed on a later wave. Separately, the bridge can merge a proposal that duplicates a job already in the queue.
- **Shipped fix (2026-07-31, [[janitor-timeout-but-artifact-ship-2026-07-31]] implemented + verified):** the timeout-credit breaker closes the PRIMARY mechanism (a timed-out session that did its work re-dispatched to redo it). On a `TIMEOUT`, if the work demonstrably LANDED, the runner credits it instead of re-claiming: (1) `artifact_gate()` (`runner.sh:185`) now handles a `TIMEOUT*` verdict — if the captured `PRODUCED` path exists it rewrites the verdict to `TIMEOUT(BUT_ARTIFACT)` and marks `[x]` via the SAME path-existence check the ok-lane uses; a bare `TIMEOUT` (no artifact / `NONE` / missing path) is returned unchanged → stays `[ ]` → re-dispatch + quarantine (the trust-bug guard stands; `SESSION_TIMEOUT` deliberately NOT raised). (2) When the kill beat the marker (`produced` empty), the collect phase recovers the artifact via `timeout_artifact()` — an mtime-in-window scan over the durable trees, bounded BELOW by the WAVE-START epoch (sampled before dispatch, same kernel clock → a prior wave's artifact can never be credited — the cross-wave phantom the sandbox caught and forced) and gated to EXACTLY-ONE in-window hit (parallel siblings ⇒ ambiguous ⇒ no credit ⇒ safe re-dispatch). (3) `TIMEOUT(BUT_ARTIFACT)` classified as bookkeeping in all four counters (Guard-2 exclusion `runner.sh:70`, `fail_streak` skip `runner.sh:178`, health.sh `NONSESSION`, evaluate.sh bookkeeping skip) like `ok(DEFERRED)`; a BARE `TIMEOUT` is deliberately absent from `fail_streak`'s skip list so it still counts as a REAL fail and still quarantines. Verified 26/26 sandbox assertions (stub-claude, zero tokens). The SECONDARY mechanism — the bridge merging a proposal that duplicates a job already in the queue (FM-6 (b)) — remains open. Pre-existing mitigations unchanged: content-matched atomic `mark_job`, in-wave write-target de-dup via `CLAIMED_TARGET`, idempotent artifacts + `VERIFIED-DUPLICATE` reporting.
- **Regression check (watch item, not a simulation):** after any change touching the claim loop / `mark_job` / the bridge, grep the next 24h of LOG for one job text appearing with two `ok` verdicts — that IS the regression signal.

## FM-7 · Gateway 502 storm — router listening, upstream dead (2026-07-28) — breaker SHIPPED 2026-07-29

- **Symptom:** every session dispatched on 2026-07-28 — 4 empty-queue Steward reflections at the 6h throttle cadence — burned 265–276s then died `exit1 · API Error: 502 Request failed after 4 attempt(s): fetch failed … check your inference gateway (localhost:8705)`; the engine produced nothing for ~24h, then self-recovered. The Guard-3 proxy preflight (FM-1) PASSED every wave — the router was listening.
- **LOG evidence:** deaths at `2026-07-28T00:49:27Z / 07:04:37Z / 13:04:30Z / 19:04:29Z` (lines 703, 728, 752, 776 as of 2026-07-29, 803-line file), each `exit1` with the 502 text; zero `SKIP(PROXY_DOWN)` lines all day (preflight passed); no `QUARANTINED` line despite 4 consecutive REAL fails (reflection jobs bypass the breaker — gap (c) below); recovery `2026-07-29T01:04:30Z ok` (line 800). ~1078s burned.
- **Root cause (gateway logs):** the router daemon never restarted (zero systemd start/stop events 07-27→29) and kept accepting connections — a 502 IS an HTTP response, so Guard-3's TCP probe (`runner.sh:55-64`, `/dev/tcp`) passed. What failed was the router's UPSTREAM fetch to Alibaba MaaS: `journalctl --user -u universal-router` shows `[proxy] Request failed (attempt 1..4): fetch failed [retryable]` (204 attempts, 51 exhausted) in bursts that line up exactly with the 4 death windows (host clock WEST = UTC+1: 01:45/08:00/14:00/20:00 local = 00:45/07:00/13:00/19:00Z, ~11 exhausted failures each); after 4 attempts the router returned 502 to the CLI. Bursts are demand-driven — visible only when the engine sent traffic. `fetch failed` is socket/DNS-level egress; the same signature hit direct SEC egress the same night ([[quant-pilot-02-RESULT]] §diagnostic: valoos ConnectionError storm 22:15Z→00:00Z, overlapped by a router-upstream burst at 23:12Z). **One local-egress instability, two surfaces; the deeper root (laptop network/DNS) is suspected, NOT verified.** The gateway 502 is NOT the direct cause of row-4's 49.8% fetch_fail — tested in [[quant-pilot-02-RESULT]]: SEC traffic never traverses :8705 (no `HTTP(S)_PROXY`), the model path through :8705 stayed 99.8% healthy during the damage window (2,968 ok / 7 model_fail), and the Steward deaths begin 00:49Z, AFTER extraction ended (00:01Z).
- **Why nothing caught it (three gaps, all evidenced):** (a) Guard 3 probes TCP only — built for a DEAD router (FM-1); a listening-but-degraded router passes. (b) The obvious HTTP probe `GET /v1/models` is served LOCALLY by the router — tested live 2026-07-29: HTTP 200 in 0.8ms, static list, no upstream round-trip — it would have returned 200 throughout the storm. (c) `fail_streak`'s infra regex (`runner.sh:112`) does NOT match the 502 text (tested: 0 hits), so the deaths counted as REAL fails — yet no quarantine fired, because the empty-queue reflection appends the Steward job directly to `J_JOB` (`runner.sh:283`), bypassing the claim-loop breaker; the engine re-fired into the storm 4× with nothing to stop it.
- **Shipped fix (2026-07-29, Guard 5 — [[janitor-gateway502-preflight-probe-2026-07-29]] implemented + verified):** (1) **Guard 5** reactive hold (`runner.sh:86-104`) + `gateway_detect()` (`runner.sh:123-128`, mirrors FM-3's `quota_detect`): match `502 Request failed after [0-9]+ attempt|check your inference gateway` in worker output → latch epoch in `_harness/.gateway_hold` (`GATEWAY_HOLD_S=1800`, `config.env:28`) → waves exit on a cheap `SKIP(GATEWAY)` until expiry → `GATEWAY_RESUMED` clears it (corrupt hold self-heals); (2) **Guard 5b** active probe (`runner.sh:130-145,257-266`, `GATEWAY_PROBE=1` kill switch `config.env:32`): authenticated `POST /v1/messages` (max_tokens=1, `x-api-key: $ANTHROPIC_AUTH_TOKEN`) exercising the router's UPSTREAM fetch — explicitly NOT `/v1/models` (gap (b)); 5xx latches the hold pre-dispatch; (3) `502|fetch failed` added to `fail_streak`'s infra regex (`runner.sh:156`) so a storm never false-quarantines queued jobs; (4) reflection breaker parity — the empty-queue Steward job now passes through `fail_streak`/`MAX_JOB_RETRIES` (`runner.sh:338-348`) → `SKIP(REFLECTION_QUARANTINE)` on breach (closes gap (c)); (5) builder/council suppressed under the hold (`runner.sh:180,408-409`). Verified in sandbox: endpoint gate (router copy, dead `UPB_BASE_URL`: `/v1/models` 200 = disqualified, authenticated POST 502 in 9.1s = qualified), hold round-trip, infra classification, reflection breaker, `bash -n` — digest [[janitor-gateway502-guard5-ship-verify-2026-07-29]].
- **Regression check:** any future day with ≥2 same-day `exit1` lines carrying `502 Request failed` = recurrence and MUST show `SKIP(GATEWAY)` lines instead of burned sessions. If the probe itself misbehaves, flip `GATEWAY_PROBE=0` (`config.env:32`) — the reactive detector remains the backstop.

## FM-8 · Phantom `[x]` + binary-poisoned audit trail (2026-07-29) — breaker SHIPPED 2026-07-29

- **Symptom:** two live bugs, one root theme — the harness trusted *process fate*, never *work state*, and never sanitized what it appended. (A) **PHANTOM COMPLETION:** the `queue.md:69` SCORE job was permanently `[x]`'d by a 49s session that produced NOTHING — dispatched ~7h before its precondition (`results.json`) existed, it took its own "too early → report → exit" branch, exited 0 → `ok` → `[x]`, with the RESULT note never written (it landed only via the re-run ~8h later). Sister face: the 02:15Z/03:45Z TIMEOUTs did work that landed in-tree UNRECORDED (the retry found it done and took the credit), and startup-reaper kills logged to stderr only — no LOG line, no job name. (B) **LOG.md binary-to-grep:** one truncated UTF-8 byte made GNU grep classify the WHOLE audit trail as binary, silently disabling Guard 2 (`ran_today` pinned at 0 while 13 real sessions ran — `MAX_SESSIONS_PER_DAY=90` could never fire) and blinding every plain-grep audit.
- **LOG evidence:** SCORE `2026-07-27T17:15:50Z | 49s | ok` vs `results.json` mtime `2026-07-28T01:01Z` (~7h after dispatch); TIMEOUT family `2026-07-29T02:15:02Z` + `03:45:01Z` (artifacts mtime 04:56Z, credited to the 02:32Z/03:57Z retries); bad bytes at LOG.md lines 632 + 655 (offsets 155341/165354: `…PBO guard <0xe2>\n` — an em dash truncated to a lone lead byte); `grep -c '^- 2026-07-29 ' LOG.md` → exit 1/nothing while `grep -ac` → 37; Guard-2 `ran_today` computed 0. Diagnosis: [[janitor-phantom-completion-diagnosis-2026-07-29]].
- **Root cause:** (1) `worker.sh:80` mapped exit 0 → `ok` and `runner.sh:401/425` mapped `ok` → `[x]` with **no artifact-existence oracle** — a deliberate no-op phantom-completes; (2) the startup reaper (`runner.sh:36-43`) + cleanup trap recorded kills on stderr only; (3) `set -uo pipefail` without `-e`: a failing `printf >> "$LOG"` in `log_line` returned non-zero and execution continued into `mark_job` — a truly silent `[x]` was a latent path; (4) the summary slice `cut -c1-200` cuts BYTES under cron's C locale (GNU cut `-c` is byte-wise even in UTF-8 locales — verified on this box), so any summary ending on a multibyte char at column 200 wrote a lone lead byte that permanently flipped the file binary (reproduced: `printf 'abcdefghij — emdash' | LC_ALL=C cut -c1-12 | od -tx1` → `…20 e2 0a`).
- **Shipped fix (2026-07-29, [[janitor-phantom-completion-fix-ship-2026-07-29]] implemented + verified):** (1) **Artifact oracle** — the worker prompt requires a final `PRODUCED: <path|NONE|DEFERRED>` marker (`worker.sh:61-66`); `worker.sh:104` captures it as a 4th verdict field; the new `artifact_gate()` (`runner.sh:185`) marks `[x]` only if `verdict==ok` AND (`NONE` or the path exists), in BOTH collect lanes (`runner.sh:445-448`, `473-476`). `DEFERRED` → `ok(DEFERRED)` = bookkeeping (excluded from Guard 2 at `runner.sh:70` + `fail_streak` skip at `runner.sh:177` + health.sh NONSESSION + evaluate.sh — never quarantined, never counts against the daily cap); missing/undeclared path → `ok(NO_ARTIFACT)` = REAL fail (counts toward `MAX_JOB_RETRIES` quarantine). (2) **REAPED line** — the worker writes `state/worker-<slot>.job` at dispatch (`worker.sh:37-39`); the startup reaper (`runner.sh:57`) + cleanup trap (`runner.sh:413`) log `REAPED | (reaper) | <job> | orphan killed — work (if any) unrecorded, job preserved [ ]` — the job is read BEFORE the kill (SIGTERM runs the worker's EXIT trap, which deletes its own sidecar — a race the sandbox caught and fixed); stale sidecars are cleared so collect can never read a dead run's verdict. (3) **Log-before-mark** — `log_line` is now `printf | iconv -f UTF-8 -t UTF-8 -c >> "$LOG" || exit 1` (`runner.sh:32-36`) and collect is `log_line … && [[ mark ]] && mark_job` — no `[x]` can ever outrun its LOG line. (4) **Stop poisoning LOG.md** — `export LC_ALL=C.UTF-8` at the top of `runner.sh:19`; the summary slice is now char-safe `sed -E 's/^(.{0,200}).*/\1/'` (verified: keeps the full em dash at char 200) with the PRODUCED marker line filtered out of the summary (`runner.sh:442,471`); every appended line is iconv-sanitized; `grep -a` added to Guard 2 + health.sh + council.sh as belt-and-braces. (5) **One-time repair** — the two lone `0xe2` lead bytes (lines 632+655) restored to em dashes in place (pre-repair backup `/tmp/LOG.md.pre-fm8-repair.bak`); `iconv` whole-file clean, `grep -c '^- 2026-07-29' LOG.md` = 37 WITHOUT `-a`, production Guard-2 `ran_today` = 13 (was 0). `SESSION_TIMEOUT` deliberately NOT raised.
